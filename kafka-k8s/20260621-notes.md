# 2026-06-21 Notes

## What was done

### 1) Traced why the chaos daemon was crashlooping
I investigated the `chaos-monkey-daemon` crash on `kafka-cluster-worker2` and found the root cause was not the chaos logic itself.

Findings:
- The daemon could not reach the Kubernetes API through the in-cluster service IP `https://10.96.0.1:443`.
- `kube-proxy` was crashlooping on several Kind nodes.
- The deeper failure in `kube-proxy` / container startup was `too many open files`, which in this cluster was the Kind/inotify issue rather than host-wide fd exhaustion.

### 2) Implemented the missing network-chaos path
The repo design called for kernel-level network disruption. I added an eBPF-based traffic shaper in the daemon path.

Key changes:
- Added an `EBPFTrafficShaper` abstraction in `src/chaos_monkey/daemon/shaper.go`.
- Implemented a TCX-based eBPF program that:
  - resolves the target pod container ID,
  - finds the host-side veth interface index,
  - loads a small eBPF classifier,
  - attaches it to ingress and egress,
  - randomly drops packets based on the configured drop percentage,
  - detaches the links when the task expires or is removed.

### 3) Updated the daemon runtime image and RBAC
To make the new traffic shaping path work in-cluster:
- Removed the old tc/netem dependency from the daemon image.
- Updated the daemonset template to run with:
  - `hostPID: true`
  - `BPF`
  - `PERFMON`
  - `NET_ADMIN`
  - `SYS_ADMIN`

### 4) Added repeatable demo assets

## Problems encountered

### Problem: daemon crashloop due to API access failure
The daemon died before doing any chaos work because it could not reach the Kubernetes service IP. This was caused by broken `kube-proxy` on the affected Kind nodes.

How I diagnosed it:
- checked daemon logs
- checked node/pod placement
- compared service-IP connectivity on healthy vs unhealthy Kind nodes
- inspected `kube-proxy` logs

### Problem: `too many open files` on Kind nodes
The error was misleading at first. It was not general fd exhaustion. The actual issue was Kind/inotify related.

What I found:
- `kube-proxy` and container startup logs showed `failed to create inotify fd: too many open files`
- host fd totals were not saturated
- Kind docs describe this as the classic inotify limit problem

### Problem: build/test needed module hygiene work
After switching the daemon from tc/netem to eBPF, the Go module needed a few dependency/version updates and missing checksum lines added back to `go.sum`.

What I fixed:
- Added `github.com/cilium/ebpf` and updated `golang.org/x/sys` in `go.mod`.
- Added the needed checksum entries for the eBPF and updated transitive dependencies in `go.sum`.
- Re-ran `go test ./...` until the `chaos_monkey` module passed.

## Notes on the implementation direction
The final implementation is now eBPF-based rather than tc/netem-based. It intentionally supports a small practical subset of network chaos:
- packet loss
- blackhole-style outage via 100% loss

Latency is not implemented in this version.
